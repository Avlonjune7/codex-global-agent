# 页面性能与加载速度

性能是设计与交互质量的一部分。优先保证真实用户体验，在不牺牲功能、可访问性和可维护性的前提下，控制加载成本与响应延迟。

- **首屏与导航**：优先呈现当前任务所需的关键内容，减少阻塞渲染的资源和非必要初始化；避免为单纯视觉效果增加首屏负担。
- **依赖与代码**：复用项目现有能力，不为小需求引入体积较大或功能重叠的依赖；在有实际收益时采用代码分割与按需加载，不盲目拆包。
- **图片、字体与图标**：使用适合展示尺寸的资源、合理压缩与现代格式；非首屏图片按需懒加载，避免关键首屏资源被错误延迟；控制字体字重和图标资源数量，预留尺寸避免布局跳动。
- **请求与缓存**：避免重复请求、串行请求瀑布和无意义的高频轮询；按业务一致性要求使用缓存、请求合并或复用，不因追求速度展示过期关键数据。
- **渲染与列表**：避免不必要的组件更新、昂贵计算和大 DOM；确有数据规模与测量依据时使用分页或虚拟列表，不为小列表增加复杂度。
- **交互与动画**：交互操作要有及时、明确的状态反馈；简单过渡优先 CSS，避免大面积布局动画、长任务和阻塞主线程的效果；尊重减少动态效果偏好。
- **加载体验**：适用时采用骨架屏、占位尺寸或渐进呈现，防止内容闪烁、跳动；不要用纯装饰性加载效果掩盖真实慢请求。
- **技术适配**：不为了性能指标强制引入 SSR、缓存服务、状态库、构建工具或更换技术栈。优先定位当前瓶颈，再选择最小有效改动。

### 性能验证

- 对涉及加载、请求、资源或渲染性能的修改，优先在目标设备和网络条件下检查首次加载、二次导航、主要交互和列表操作；必要时分别检查移动端与桌面端。
- 对适用的 Web 页面，以真实用户体验为导向，参考 Core Web Vitals 的良好阈值：LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1；优先参考第 75 百分位的实际用户数据，区分设备与网络环境。这些不是所有项目的强制验收门槛。
- 可按需使用浏览器 Performance、Network、Lighthouse 或已有监控，定位具体阻塞、体积、请求或布局问题；自动评分不能代替真实操作与视觉检查。
- 优化前后尽可能使用可比较的测试环境，记录关键变化及其代价；没有测量数据时不声称“显著提速”或给出虚构的百分比。
- 对个人工具和轻量后台，优先消除明显瓶颈与无必要资源，不为跑分牺牲功能完整性、开发效率或维护成本。
